# members_sync - архитектура

Раз в сутки (03:00 МСК) сервис синхронизирует участников из Google Sheets в Postgres. Он переживает изменения структуры
таблицы, не теряет данные и сообщает об ошибках парсинга заметками к ячейкам.

Решения владельца:
1. Ошибки парсинга - заметки к ячейкам (gspread notes), а не комментарии.
2. Пропавшие из таблицы участники не удаляются.
3. Схема - одна таблица `lbg_members` плюс сырой снимок в JSONB (модель `LbgMember` в `best_db`).
4. Ключ upsert - email `@best-eu.org`, запасной - нормализованное русское ФИО.

## Источник данных

| Лист                                   | Раскладка | Категории                          |
|----------------------------------------|-----------|------------------------------------|
| `Database of Members`                  | A         | board, full, baby, observer        |
| `Alumni+Former+abroad+guests+inactive` | B         | alumni, former, abroad, guest, inactive |
| `Ex-members`                           | B         | ex-full, ex-baby                   |

Что диктует архитектуру:
- **Колонки различаются между листами**, поэтому они определяются по тексту заголовка, а не по индексу.
- **Один участник - две строки:** в первой русское ФИО и большинство полей, во второй английское ФИО, Telegram/Facebook
  и учебная группа (`3733806/20102`).
- **Секции-заголовки** (`BOARD`, `FULL MEMBERS`, ...) идут отдельной строкой: колонка 0 пуста, в колонке 1 название.
- **Внизу листа** статистика и пустые строки: конец данных определяется по нескольким пустым строкам подряд, строке
  `Statistics:` или строке, не похожей на участника.
- **Данные грязные:** телефоны в 5+ форматах, американские даты, переставленные ФИО, несколько значений в ячейке.

## Принципы устойчивости

1. **Колонки по заголовкам.** `SheetSpec` задаёт для поля набор алиасов заголовка, без учёта регистра, пробелов и
   `ё`/`е`. Перестановка или переименование колонки не ломают парсер, пока заголовок узнаваем.
2. **Конфигурация листа отделена от кода:** строки заголовка, высота записи, какие поля из какой строки, детект секции.
3. **Нормализатор не бросает исключений:** `raw_str -> (value, ParseIssue | None)`. Запись синхронизируется всё равно.
4. **Сырой снимок.** В `raw` (JSONB) лежат все исходные значения и источник: данные не теряются, перепарсить можно без API.
5. **Никаких DB-enum:** новая секция в таблице не требует миграции.
6. **Идемпотентность:** прогон над неизменной таблицей меняет только `last_synced_at`, заметки перезаписываются и снимаются.

## Код

```
sheets/    доступ к Google Sheets: spec.py, column_mapper.py, record_reader.py, notes.py
parsing/   fields.py, normalizers.py, issues.py, member_builder.py
database/  свой engine и методы upsert/deactivate; модель и alembic - в best_db
sync/      service.py (оркестратор), report.py
run.py     точка входа: RUN_MODE=once (для внешнего планировщика) или cron (apscheduler)
```

## Один прогон

```
run.py -> sync.service.run()
  1. SheetsClient.open(SPREADSHEET_KEY)
  2. values_batch_get по всем листам
  3. для каждого листа: ColumnMapper.resolve -> RecordReader.iter_records -> MemberBuilder.build
  4. дедуп по identity_key между листами
  5. upsert в БД
  6. deactivate_missing: кого не было в прогоне
  7. NotesWriter.flush, если WRITE_SHEET_NOTES
  8. ReportWriter: отчёт .md и output/members.json
```

Чтение укладывается в 3 запроса к API на все листы: `worksheets()`, `values_batch_get`, `fetch_sheet_metadata`. Запись
заметок - один `batch_update`. Запросы на каждый лист упирались в латентность и rate-limit Google. Ключевые шаги пишут
`elapsed_s` в лог.

## Идентичность и членство

`identity_key` (`UNIQUE`) - `lower(best_email)` для `*@best-eu.org`, иначе русское ФИО в нижнем регистре со схлопнутыми
пробелами и `ё→е`. Человек сразу на двух листах получает заметку «дубликат», а побеждает запись с большим
`membership_precedence`: активная > alumni > former/inactive > исключённая.

Секция задаёт `Membership` (`parsing/fields.py`). `is_active` - может брать таски группы, `is_excluded` - исключён из
группы. Alumni и former не активны, но не исключены: доступ к ресурсам бота у них сохраняется.

| Лист | Секция                     | `membership_category`        | `is_active` | `is_excluded` |
|------|----------------------------|------------------------------|-------------|---------------|
| 1    | BOARD, FULL, BABY, OBSERVERS | `board`, `full_member`, `baby_member`, `observer` | да |   |
| 2    | ALUMNI, Former, Inactive   | `alumni`, `former`, `inactive` |           |               |
| 2    | Abroad, Guest              | `abroad`, `guest`            | да          |               |
| 3    | EX-FULL, EX-BABY           | `ex_full_member`, `ex_baby_member` |       | да            |
| нет  | пропал из всех листов      | сохраняется прошлая          |             | без изменений |

Пропавшая запись получает `is_active=false` и `removed_from_sheet_at=now()`. `is_excluded` не трогаем: пропажа из таблицы
и исключение из группы - разные события.

Поля модели - в `best_db/models`. Принцип: типизированное поле плюс `*_raw` для неоднозначных значений.

## Нормализаторы

Подробности - в `parsing/normalizers.py`.
- **phone:** `8→7`, 10 цифр → `+7…`; первый номер в `phone`, весь текст в `phone_raw`.
- **date:** `dd.mm.yyyy`, `yyyy-mm-dd` и американские `m/d/yyyy`, `m.d.yyyy`. При `day>12` меняем местами, при
  неоднозначности - `None` и `ParseIssue`.
- **active period:** `March 2024`, `March 2015 - May 2018`, `Sep 22'` → `active_since`, `active_till`.
- **vk, telegram, facebook, instagram:** url или `@handle`. **gender:** `female`, `male`. **study_group:** мягкая проверка.

## Заметки к ячейкам

`NotesWriter` копит `(sheet, A1, text)` и пишет батчем. Маркер `🤖 [sync]…` позволяет не затирать заметки людей и снимать
свои, когда ошибка исправлена. Включается `WRITE_SHEET_NOTES` (по умолчанию выключено), нужно право редактирования.

## Схема БД

Модели и единый alembic - в `packages/db`. В dev сервис может создать только свою таблицу (`AUTO_CREATE_SCHEMA`), в проде
схему накатывает alembic (`make migrate`, сервис `db_migrate`). `Person.lbg_member` - необязательная связь для опознания
участника, написавшего боту.

## Известные риски

- Даты `m/d` и `d/m`: эвристика плюс issue, 100% точность недостижима.
- ФИО как запасной ключ неустойчиво к смене фамилии и опечаткам.
- Запись без `@best-eu.org`, личной почты и ФИО пропускается с ошибкой в отчёте.
- Участник с одной строкой обрабатывается как запись из одной строки, EN-поля пусты.
