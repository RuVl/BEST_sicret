# Принципы чистого кода в BEST sicret

Свод правил для этого репозитория: чем руководствоваться, когда пишешь новый экран, метод БД
или интеграцию. Не общая теория — только то, что вытекает из архитектуры проекта
(aiogram 3 + aiogram-dialog 2 + SQLAlchemy 2.0 async) и из ошибок, которые тут уже допускались.

Общая рамка проекта — в [CLAUDE.md](CLAUDE.md), устройство `members_sync` —
в [members_sync/ARCHITECTURE.md](members_sync/ARCHITECTURE.md).

---

## 1. Слои и направление зависимостей

```
handlers/  →  state_machines/  →  dialogs/  →  includes/  →  database/methods/  →  best_db.models
(команды)     (состояния)         (UI)         (домен,       (репозиторий)         (схема)
                                               внешние API)
```

- Зависимости идут **только вниз**. `database/methods/` ничего не знает про диалоги,
  `includes/vpn/` — про aiogram.
- Хэндлер команды не содержит логики: он стартует состояние и всё
  (`bot/handlers/commands.py`).
- Модуль отвечает за одно: `formatters.py` — только форматтеры, один метод — один файл
  в `database/methods/<entity>/`.
- Циклы импорта разрываем ленивым импортом внутри функции или `TYPE_CHECKING`
  (см. `bot/includes/templates/main.py`).

## 2. aiogram-dialog: правила, которые нельзя нарушать

Библиотека построена на двух идеях: **загрузка данных отделена от отрисовки** и **кнопка сама
обрабатывает свой клик**. Из этого следует остальное.

### 2.1 Окно самодостаточно

Геттер обязан сам добыть всё, что рисует. Он не имеет права рассчитывать, что кто-то снаружи
(middleware, родительский диалог) уже положил данные.

**Почему это жёсткое правило.** Когда поддиалог стартует из кнопки родителя, событие
обрабатывает роутер **родителя**. Middleware, навешанная на поддиалог, не сработает, а его окно
уже рисуется — геттер упадёт на пустых данных. Именно так этот проект получил
`KeyError: 'person'` при открытии VPN-экрана из профиля.

```python
# Плохо: геттер верит, что данные кто-то положил
person = dialog_manager.middleware_data["person"]

# Хорошо: геттер сам опознаёт пользователя и грузит данные
user = dialog_manager.event.from_user
async with async_session() as session:
    person = await get_person_with_member(session, user.id)
```

Текущего пользователя всегда берём из `dialog_manager.event.from_user`.

### 2.2 Доступ проверяется там, где принимается решение

`when=` у виджета — это **подсказка интерфейса, а не защита**. Клавиатура у пользователя может
быть старой, а кнопка — нажатой повторно.

- Право проверяем в геттере (что показать) и в `on_click` (что сделать).
- Не пишем middleware ради гейта одного диалога: она усложняет поток и, как описано выше,
  срабатывает не всегда. Middleware — для сквозных вещей на весь `Dispatcher`
  (локализация, логирование), и они регистрируются в одном месте — `bot/middlewares/main.py`.

### 2.3 Middleware-данные: в геттере — аргументы, в `on_click` — нет

```python
async def get_data(dialog_manager, l10n: FluentLocalization, log, **kwargs): ...   # придут сами

async def on_click(clb, widget, dialog_manager):
    l10n = dialog_manager.middleware_data[L10N_FORMAT_KEY]   # только так
```

Обработчик клика вызывается как `callback(event, widget, manager)` — никаких kwargs. Ключи
берём из констант `L10N_FORMAT_KEY`/`LOGGING_KEY`, не из строковых литералов.

### 2.4 Переходы — виджетами, а не руками

| Задача | Инструмент |
|---|---|
| другое окно того же диалога | `SwitchTo`, `Next`, `Back` |
| открыть поддиалог | `Start` |
| закрыть диалог, вернуться к родителю | `Cancel` (или `dialog_manager.done(result=…)`) |
| стартовать диалог из команды | `dialog_manager.start(..., mode=StartMode.RESET_STACK)` |

Свой `on_click` пишем, только если помимо перехода есть логика. `Start(data=…)` задаётся при
конструировании и **статичен** — динамику через него не передать; либо грузим данные в геттере
поддиалога (предпочтительно), либо стартуем вручную через `dialog_manager.start(..., data=…)`.

### 2.5 Не перерисовывай окно вручную

В приватном чате любой обработанный клик уже вызывает `dialog_manager.show()` — геттер
отработает заново. Кнопке «Обновить» не нужен `on_click`, а вызывать `show()` из обработчика
не надо.

### 2.6 Стек диалогов

- Команда-точка входа: `StartMode.RESET_STACK` + `launch_mode=LaunchMode.ROOT` у диалога —
  иначе повторные вызовы копят контексты в стеке.
- `start_data`, `dialog_data` и данные виджетов лежат в FSM-хранилище. Кладём туда только
  идентификаторы и примитивы — **не ORM-объекты**.
- Объекты контекстов шаблонов пикулятся в Redis: при изменении их формы бампаем
  `BaseContext.__version__`.

## 3. База данных

- **Репозиторий**: маленькие `async def` в `database/methods/<entity>/`, принимают `AsyncSession`,
  содержат запрос и ничего больше. Логика — выше по слоям.
- **Коммитит вызывающий**: `async with async_session() as session: … await session.commit()`.
  Внутри метода репозитория `commit()` не бывает.
- **Никаких ленивых подгрузок после закрытия сессии.** Нужны связи — грузим явно
  (`joinedload`, `selectinload`) или через `await obj.awaitable_attrs.<rel>` внутри сессии.
  `expire_on_commit=False` спасает только уже загруженные поля.
- Модели живут **только** в `packages/db` (`best_db.models`) — единый владелец схемы для бота
  и `members_sync`. Новая модель = правка трёх мест: файл модели, `best_db/models/__init__.py`
  и ручной ре-экспорт `bot/database/models/__init__.py`.
- Миграции — одна история в `packages/db`, создаются только через `make migration m="…"`,
  сгенерированный файл читаем глазами перед `make migrate`.

## 4. Внешние интеграции

- Клиент внешнего API живёт отдельно от домена: транспорт (`client.py`), схемы (`schemas.py`),
  свои исключения (`exceptions.py`), доменные операции (`service.py`).
  Пример — `bot/includes/vpn/`.
- Ответы разбираем в pydantic-модели, а не таскаем словари по коду. Поля именуем по смыслу,
  расхождение с API закрываем `alias` и комментарием (в 3x-ui поле `totalGB` хранит **байты** —
  у нас оно называется `total_bytes`).
- Ошибки транспорта заворачиваем в собственный тип (`XuiError`) и ловим **на границе UI**:
  пользователь видит текст из `.ftl`, бот не падает, в лог уходит `structlog`-событие.
- Секреты — в конфиге, в логи не попадают никогда.
- Контракт сверяем с первоисточником (исходники/OpenAPI-схема), а не с постами и блогами.
  Догадки о формате запроса помечаем и проверяем эмпирически до мержа.

## 5. Тексты, локализация, MarkdownV2

- Ни одной пользовательской строки в коде — всё в `bot/l10n/<locale>/*.ftl` через
  `l10n.format_value(key, args=…)`.
- Parse mode — **MarkdownV2**. Любое динамическое значение прогоняем через `escape_mdv2`.
  URL показываем инлайн-кодом: так спецсимволы не ломают разметку.
- Ловушки Fluent, на которых уже обжигались (обе проявляются молча — ключ возвращается вместо
  текста или сообщение обрывается):
  - **пустая строка обрывает сообщение** — пустой абзац пишем как `{ "" }` с отступом;
  - **строка не может начинаться с `*`** (это синтаксис вариантов) — оборачиваем в `{ "*…*" }`;
  - в строковых литералах Fluent нельзя `\(` — экранирование MarkdownV2 выносим за литерал
    или переформулируем текст без скобок.
- Новые ключи закрываем тестом (`bot/tests/test_l10n_keys.py`): он ловит и необъявленный ключ,
  и обрыв многострочного шаблона.

## 6. Конфигурация

- Только `pydantic-settings`: секция — отдельный `BaseSettings`, все секции собираются на
  `GlobalSettings` (`bot/env.py`). Обращение — `settings.<секция>.<ПОЛЕ>`.
- Имя переменной окружения задаём через `alias=`. Списки в `.env` — строка через запятую
  плюс `NoDecode` и `field_validator`, а не JSON.
- Каждую новую переменную добавляем в `*.env.dist` с плейсхолдером.
  **Реальные `*.env` не читаем и не правим.**
- Функциональность, зависящая от внешнего сервиса, должна уметь быть выключенной: проверяем
  полноту секции (`settings.xui.ENABLED`) и не поднимаем фоновые задачи впустую.

## 7. Типы, стиль, комментарии

- Аннотируем всё. Современные объединения (`str | None`), `Literal[...]` для конечных наборов,
  дженерики (`list[Category]`, `async_sessionmaker[AsyncSession]`).
- `BaseModel`/`BaseSettings` — для конфигов и внешних контрактов, `@dataclass` — для простых
  переносчиков данных.
- Имена: `PascalCase` классы, `snake_case` функции, `CONSTANT_CASE` константы-действия,
  `_`-префикс у приватного.
- Комментарии и докстроки — **на русском**, объясняют **почему**, а не «что». Разделители
  `# ========== … ==========` внутри диалогов приветствуются.
- Длина строки 120, форматирование и импорты — `make format`, проверка — `make lint`.

## 8. Тесты

Есть смысл покрывать: чистые функции (выбор идентификатора, форматирование), разбор ответов
внешнего API по фикстурам, выборку «кого затрагиваем», ключи локализации.

Нет смысла: сеть, живую БД, отрисовку окон. Тесты бота не должны требовать ни того, ни другого —
`bot/tests/conftest.py` подсовывает минимальные переменные окружения, и всё.

## 9. Чек-лист перед PR

- [ ] `make lint` и `make test` зелёные.
- [ ] Новая модель отражена во всех трёх местах, миграция сгенерирована `make migration` и прочитана.
- [ ] Геттеры не зависят от middleware; право доступа проверяется в геттере и в обработчике.
- [ ] Пользовательские строки — в `.ftl`, динамика экранирована, ключи покрыты тестом.
- [ ] Новые переменные окружения — в `.env.dist`/`dev.env.dist`.
- [ ] Ошибки внешних сервисов не роняют бота и видны в логах.
- [ ] Комментарии объясняют неочевидное «почему», а не пересказывают код.
