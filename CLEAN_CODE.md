# Принципы чистого кода в BEST sicret

Только то, что вытекает из архитектуры проекта и из ошибок, которые тут уже допускались. Обзор проекта - в
[CLAUDE.md](CLAUDE.md), устройство `members_sync` - в [members_sync/ARCHITECTURE.md](members_sync/ARCHITECTURE.md).

## 1. Слои

```
handlers/  →  state_machines/  →  dialogs/  →  includes/  →  database/methods/  →  best_db.models
(команды)     (состояния)         (UI)         (домен, API)  (репозиторий)         (схема)
```

- Зависимости идут только вниз: `database/methods/` не знает про диалоги, `includes/vpn/` - про aiogram.
- Хэндлер команды не содержит логики: он только стартует состояние.
- Один модуль - одна задача, один метод БД - один файл в `database/methods/<entity>/`.
- Циклы импорта разрываем ленивым импортом или `TYPE_CHECKING` (см. `bot/includes/templates/main.py`).

## 2. aiogram-dialog

### 2.1 Окно самодостаточно

Геттер сам добывает всё, что рисует. Поддиалог, стартованный кнопкой родителя, обрабатывает роутер родителя, поэтому
middleware поддиалога не сработает. Так проект получил `KeyError: 'person'` при открытии VPN-экрана.

```python
# Плохо
person = dialog_manager.middleware_data["person"]

# Хорошо
user = dialog_manager.event.from_user
async with async_session() as session:
    person = await get_person_with_member(session, user.id)
```

### 2.2 Доступ проверяется там, где принимается решение

`when=` - подсказка интерфейса, а не защита: клавиатура могла устареть. Право проверяем в геттере и в `on_click`.
Middleware ради гейта одного диалога не пишем: они только для сквозных вещей и регистрируются в `bot/middlewares/main.py`.

### 2.3 Middleware-данные: в геттере аргументы, в `on_click` нет

```python
async def get_data(dialog_manager, l10n: FluentLocalization, log, **kwargs): ...   # придут сами

async def on_click(clb, widget, dialog_manager):
    l10n = dialog_manager.middleware_data[L10N_FORMAT_KEY]   # только так
```

Ключи берём из констант `L10N_FORMAT_KEY` и `LOGGING_KEY`.

### 2.4 Переходы и перерисовка

| Задача                               | Инструмент                                           |
|--------------------------------------|------------------------------------------------------|
| другое окно того же диалога          | `SwitchTo`, `Next`, `Back`                           |
| открыть поддиалог                    | `Start`                                              |
| закрыть диалог, вернуться к родителю | `Cancel` или `dialog_manager.done(result=…)`         |
| стартовать диалог из команды         | `dialog_manager.start(..., mode=StartMode.RESET_STACK)` |

- Свой `on_click` пишем, только если кроме перехода есть логика.
- `Start(data=…)` статичен: динамику грузим в геттере поддиалога или стартуем через `dialog_manager.start(..., data=…)`.
- В приватном чате обработанный клик сам перерисовывает окно: `show()` вручную не вызываем.

### 2.5 Стек диалогов

- Точка входа: `StartMode.RESET_STACK` и `launch_mode=LaunchMode.ROOT`, иначе контексты копятся в стеке.
- В `start_data`, `dialog_data` и данные виджетов кладём только идентификаторы и примитивы, не ORM-объекты.
- Контексты шаблонов пиклятся в Redis: при изменении их формы бампаем `BaseContext.__version__`.

## 3. База данных

- Методы репозитория - маленькие `async def`, принимают `AsyncSession` и содержат только запрос.
- Коммитит вызывающий, внутри метода `commit()` не бывает.
- После закрытия сессии ленивых подгрузок нет: связи грузим явно (`joinedload`, `selectinload`, `awaitable_attrs`).
- Новая модель - правка двух мест: файл в `packages/db` и `best_db/models/__init__.py`. Импорт - из `best_db.models`.
- Миграции создаём только через `make migration m="…"` и читаем файл перед `make migrate`.

## 4. Внешние интеграции

- Есть библиотека - берём её модели и исключения напрямую, без обёртки-копии. Тонкий слой оставляем, только если он несёт
  логику бота. Пример - `bot/includes/vpn/panel.py` поверх `py3xui` (форк RuVl/py3xui, закреплён на теге).
- В 3x-ui поле `totalGB` (`Client.total_gb`) хранит **байты**, а панель заменяет клиента телом запроса: клиента сначала
  читаем, потом правим и отправляем обратно.
- Ошибки панели ловим на границе UI через `PANEL_ERRORS`: пользователь видит текст из `.ftl`, в лог идёт
  `panel_error_text(exc)`. `str(ValidationError)` не логируем: в него попадают ключи клиента.
- Секреты - в конфиге, в логи не попадают никогда.
- Контракт сверяем с исходниками или OpenAPI-схемой, догадки проверяем до мержа.

## 5. Тексты и MarkdownV2

- Все пользовательские строки - в `bot/l10n/<locale>/*.ftl`, вызов `l10n.format_value(key, args=…)`.
- Любое динамическое значение прогоняем через `escape_mdv2`. URL показываем инлайн-кодом.
- Ловушки Fluent, обе проявляются молча:
  - пустая строка обрывает сообщение: пустой абзац пишем как `{ "" }` с отступом;
  - строка не может начинаться с `*`: оборачиваем в `{ "*…*" }`;
  - в литералах нельзя `\(`: экранирование выносим за литерал или обходимся без скобок.
- Суффикс ключа определяет экранирование. Без суффикса - сообщение с MarkdownV2, спецсимволы экранированы. Без
  экранирования: `-btn` (кнопка), `-url` (ссылка кнопки), `-alert` (`clb.answer`), `-part` (кусок, который код сам
  экранирует при вставке).
- `bot/tests/test_l10n_keys.py` проверяет все ключи сам. Упал на экранировании - сначала проверьте суффикс ключа.

## 6. Конфигурация

- Только `pydantic-settings`: секции собираются на `GlobalSettings` (`bot/env.py`), обращение `settings.<секция>.<ПОЛЕ>`.
- Имя переменной задаём через `alias=`. Списки - строка через запятую плюс `NoDecode` и `field_validator`.
- Новую переменную добавляем в `*.env.dist`. **Реальные `*.env` не читаем и не правим.**
- Функция, зависящая от внешнего сервиса, должна уметь быть выключенной (`settings.xui.ENABLED`).

## 7. Стиль

- Аннотируем всё: `str | None`, `Literal[...]`, дженерики. `BaseModel` - для конфигов и контрактов, `@dataclass` - для данных.
- `PascalCase` классы, `snake_case` функции, `CONSTANT_CASE` константы, `_` у приватного.
- Комментарии и докстроки на русском, объясняют **почему**. Разделители `# ========== … ==========` в диалогах приветствуются.
- Длина строки 120, `make format` и `make lint`.

## 8. Тесты

Покрываем решения бота: чистые функции, реакцию на ошибки внешних сервисов, выборку «кого затрагиваем», ключи локализации.

Не покрываем библиотеки (подменяем их, разбор ответов проверяет сама библиотека), сеть, живую БД и отрисовку окон. Тест,
который только сверяет вызов мока или пересказывает константу, не нужен.
